## 根因与 RED

旧 `applyBusinessRules` 只从标题、描述和 facts 读取风险。仅把“电池供电”放在当前 SKU 原始规格时，实际 `AmazonService.createDraft` 仍产生 `batteries_required=false`、危险品 `not_applicable`、证书 `Not Applicable`；相同文本放标题则抑制这些默认值。首个实际 SQLite + demo/haul 测试在生产修复前失败：false 应为 undefined。

仅扩大默认值输入仍不足以阻断旧草稿：已有 attributes、历史 business report、source/human confirmed false 都会保留；旧有效 preview 可以继续提交。正式反例在修复前出现“Missing expected rejection”。REUSED 原先只返回独立 issues，不改变返回 draft 或持久化状态；加强断言后出现 DRAFT 应为 BLOCKED。自动队列只看旧通用失败原因时，此冲突归为 SYSTEM_REPAIR 而不是 NEEDS_INPUT；固定 typed cause 的正式测试先复现再修复。

扩展早期集合出现 3 pass / 9 fail，其中配方采购价格 fixture 写成 `.1` 被原入口拒绝，改为合法 `0.1` 后单独确认同一默认值根因仍为 RED。自动分类初始 fixture 未建立确定失败的 image workflow，会被原 UNKNOWN 优先级正确拦截；改为已知 BLOCKED fixture 后确认分类 RED。均未为测试放宽生产验证。

## 当前范围与声明规则

新增 `src/main/amazon/declaration-safety.ts` 统一有限风险输入和当前冲突诊断。选中普通 SKU 的 `sourceSpec`、`originalSpec`、`normalizedSpec` 分别参与；销售配方读取所有实际 components 对应的原 SKU 三种文本及 component specification，不拉入其他 siblings。sales projection 会改 anchor SKU 和 normalized display，因此先针对原始商品验证实际配方身份，再取原组件；不把投影后 SKU 当作来源 SKU 再校验。

风险词仍使用原规则：动力风险与 physical/compliance 风险分开，化学物品不构成电池肯定事实。原 physicalRisk 未覆盖英文 `electric/rechargeable/batteries`、而 batteryRisk 覆盖的差异保持原状，留作独立问题；未扩词典或引入 NLP。普通未说明资料继续原默认策略。没有风险词不表示已核实安全或合规；原有词法对“无电池”等一般否定句的行为也未泛化改写。

Haul 新草稿遇到明确当前风险，不套用对应 false/NA 默认值。已有 attrs 和 report 不自动删除、纠正或迁移；与当前风险相冲突的 false/NA 产生固定 `DECLARATION_SOURCE_CONFLICT`，`severity=ERROR`、`category=compliance`、`source=local`、`autoFixable=false`。诊断独立于 `ordinaryDeclarations` 开关，也适用于 PARENT 早退前当前 recipe。standard 保持旧行为。

诊断对已识别电池声明字段的既有合法否定值作局部处理：例如 confirmed `是否需要电池=否` 不会仅因字段名含“电池”便与自身冲突。它不能消除标题、描述、其他 facts 或所选 raw/current/normalized 规格中的独立风险；state=conflicting 也不能借此降级。该排除仅用于新诊断，不改旧默认值抑制策略。危险品与证书的合法 NA 继续既有识别方式。不会把电气风险反推为 batteries=true 或具体危险品／证书事实。

## 实际授权与持久化

- `validateDraft` / service validate 每次重算当前声明错误；save 即使清空 issues，下次 validate/preview 仍阻断。
- `prepareDrafts` REUSED 重算后把错误和 BLOCKED 写回记录及返回 draft，清当前 preview 权限，保留 attributes、business report 和旧 exchanges。
- preview 通过同一 validate；新 compliance ERROR 不满足 missing-only 例外，不能交给 provider 绕过。
- submit 在 `beginWrite` 前重算。发现该错误时先持久化 BLOCKED 与诊断、撤销当前 preview，再抛出本地校验错误。正式测试断言 beginWrite 调用 0、mock listing transport 请求 0、write locks 0；不会制造 UNKNOWN。
- transport 的既有发送 guard 再检查当前声明。未改变原请求未知状态、锁协议或重放权限。save / applyBusinessDefaults 保留旧值或旧 preview 也不能取得新授权。

自动任务消费固定结构化 issue，把仅此冲突记为 NEEDS_INPUT 并保留待修复队列；不靠 message regex，不将其本身升级 RULE_FILTERED。原 UNKNOWN 最高优先以及独立可靠 ROI/IP 筛除优先级不变，没有物理删除商品。

重开和加密备份验收按原 draft ID 读取并直接比较原商品 JSON、sourceStamp、attributes、business report、旧 exchanges、fieldAdoptions、contextSha256，以及 ai_calls / ai_results / ai_usage_ledger 的完整合成行；配方测试单独比较原 plan 和 source JSON。恢复后清 issues 再验证仍阻断，历史和值不被静默改写。
