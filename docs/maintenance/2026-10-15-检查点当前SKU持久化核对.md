# 检查点当前 SKU 持久化核对

本分包从 `74613b4` 开始，只调整检查点与 `save` 的局部核对，不改恢复入口、自动业务调度、Schema、备份或真实任务数据。

## 已放弃的整条原文方案

最初尝试每次 UPDATE RETURNING 整条 record_json，并保存实际原文，以便无关连接提交后直接比较原文，避免 JSON.parse 与整任务 deepEqual。目标 RED 已观察到 whole task parse；该方案的3条新测试和4条原检查点/CAS测试均通过，类型检查通过，但性能取舍不成立，代码已撤回，不合入。

对已归档330任务原件只读取一次原文，后续只在 memory SQLite 测量：原文约1298439字节/1151638字符，5组各10次短操作取中位。无 RETURNING 的 UPDATE 约2.108ms；TEXT RETURNING 约3.927ms，额外1.819ms；BLOB RETURNING 约3.086ms，额外0.978ms。无关提交后的原 SELECT+parse+deepEqual+UPDATE 约7.421ms；TEXT 原文比较方案约6.030ms、BLOB约2.998ms。这些是隔离内存 SQL 微基准，不是实际上架速度。

主进程实际 profile 中全文 SELECT 为7/52（约13.5%），不足以抵消每次保存 RETURNING 的成本，因此不引入任何每次保存的全文返回或原文缓存。

## 当前实现

保留 data_version 守卫。调用方明确提供 changedKeys，且 checkpoint 原修订、不可变范围及 SKU key 布局仍匹配、不是结束状态、写入 SKU 不超过原有100项全量切换门槛时，只读取持久化任务头（排除items）及本次写入项，与既有 checkpoint 的相应部分核对。completed 所需证据项加入同一写入/比对集合。

局部核对后**不更新整任务 data_version 已核验标记**。即使随后自己的保存推进了任务 revision，未检查的其他 SKU 仍脏；其持久化内容由 JSON 局部更新保留，轮到其写入时仍必须比较，发生同修订篡改就拒绝。没有显式 keys、结束状态、范围变化、缓存 revision 不匹配的回滚恢复等情形继续走原完整读取、校验与 CAS 路径。

未引入新缓存层、迁移、索引、trigger 或后台写库。SQLite仍处理整行JSON，不能宣称物理存储已独立为每个SKU。
