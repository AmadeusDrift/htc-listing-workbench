# 隔离HTTP夹具：准备期排除Fetch禁用端口

此项仅修改 `tests/fixtures/stabilization/slow-http.ts` 与独立回归，不改生产transport、原网络守卫、超时、UNKNOWN、次数、费用或旧保护断言。由S03在主进程临时授权的共享夹具窗口实施；其他树需通过已审查提交引入，不复制本地旧源码。

S03冻结 `3d61f23` 的17个完整相关文件195项194过/1败。唯一失败为choice-error用例期待回环POST1、实际0；原异常已按UNKNOWN停止。原运行没记录端口，因此**未证明这一个原事件的唯一根因**，完整红日志/metadata保留于本树 `artifacts/stabilization/s03-contract-v2/related-frozen-3d61f23-v1.*`。诊断完整domain49/49与四unknown4/4当时复跑通过，不能用复跑掩盖原红。S08曾有一例0fulfilled/0POST，此处没有证明它与本问题同因。

真实受控反例：仅在准备期把原slowHttp首次listen(0)绑定4045，实际AiService收到NETWORK_ERROR/SENT_UNKNOWN，HTTP0、adapter调用1、保留原call；原call开始到结束17ms，abortSource NONE。raw fetch错误为TypeError/fetch failed、cause bad port（3.263ms、signal未abort），原HTTP1断言失败。成功trace同时显示本机OS分配低端口（如1756、4573、4575），所以随机取得受禁端口这一夹具风险可达。反例没有付费或外部业务请求。

依据：[WHATWG Fetch 2.9 Port blocking](https://fetch.spec.whatwg.org/#port-blocking)，2026-10-15读取，页面更新时间2026-10-06；并直接只读核对本机Node `v24.21.0` 的内建Undici `7.29.1` 源badPorts列表。静态集合取其实际列表并包含无效分配0；运行不依赖私有Node API或在线查询。4045在两者列表中。只因监听成功不意味着fetch允许该端口。

最小修复：仅在服务准备阶段检查实际分配端口。若受禁，正常关闭自己刚绑定的服务后再次listen(0)；最多8次，耗尽明确抛 `STABILIZATION_FETCH_SAFE_PORT_UNAVAILABLE`。不探测HTTP、不发送业务请求、不sleep、不指定扫描其他端口、不接管/关闭其他服务；监听本身失败直接报错。普通合法端口的正文延迟、断流和取消行为保持。

新两个完整回归先RED0/2，再GREEN2/2：首4045被关闭后取得安全随机端口，原请求只POST1；连续8次4045耗尽时fetch0、所有自有server均未监听。随后用**原category choice-error完整断言**强制首4045再准备，GREEN1/1、实际安全端口1756/POST1，UNKNOWN及重复继续0新POST断言保持。提交前typecheck/boundaries exit0。正式新冻结相关验收由S03共用叶子记录补充，不能把本窄验证称为最终整链通过。
