## 已提交原 SKU 修正

`ListingCorrections` 是独立窄服务，普通草稿的 immutable 限制没有放宽。界面入口位于“确认提交与状态回读”区域，只能准备、预览、确认发送、核对或取消固定自引用删除案，不接收任意 patch JSON。

1. **准备**：绑定原 draft/revision、seller、marketplace、SKU、productType、target generation；原 `submitStarted=true` 但具有可信 ACCEPTED 回执可以进入，未核实/UNKNOWN 提交不能进入。用户点击准备后才读取当前远端属性和对应当前 PTD。
2. **身份与差异**：响应 SKU 必须匹配、attributes 必须为对象、summaries 必须为数组。非空 summaries/productTypes 必须严格匹配目标站点和类型；若 productTypes 出现，必须符合官方数组结构；所有实际出现的 `marketplace_id` 不得跨站点。
3. **空摘要**：原 48 归档 `summaries=[]`，不能伪造摘要。允许基于原可信 ACCEPTED 提交的固定商品类型及当前相应 PTD 准备；界面明确显示类型依据，仍须 PATCH 预览通过才能 READY。
4. **完整规则与局部回读**：GET attributes 可能省略未修改的业务字段，不能把它当作完整 PUT 表单。本地完整规则校验针对原可信提交 exchange.request.attributes 应用同一删除，并核对其与原 draft 属性一致；remote 目标边必须与原提交边精确一致。remote before/after 及其本地诊断单独保存；不会把缺失值补入 PATCH，也不会将原提交属性冒充当前远端属性。
5. **预览**：再次核对当前远端基线、配置和 PTD；仅 PATCH VALIDATION_PREVIEW 的有效无 ERROR 结果可 READY。旧准备、配置/Schema/基线变更都失效。
6. **发送**：renderer 仅传 id/revision/patchHash，主进程原生窗口显示原 SKU 和差异并取得用户确认。确认后再次 GET/PTD 核对，事务内竞争同 SKU 写锁并冻结单次发送意图。正式 PATCH 最多一次，网络断开、5xx 或成功 HTTP 的不完整响应记 UNKNOWN，不重发。
7. **核对**：ACCEPTED 不代表修正完成；仅专用回读看到目标自引用明确消除才 VERIFIED，展示其他平台 issues，VERIFIED 不代表可售。UNKNOWN 即使读到目标关系消除仍保持 UNKNOWN 和锁。重新授权后只允许同身份当前凭据做只读核对，请求期间 generation 必须稳定；不会恢复 READY 或发送许可。

PATCH 使用 `/attributes/package_contains_sku` 的 `delete`，value 保留 Schema selectors `marketplace_id`、`sku`，原 quantity 可保留。当前窄案仅支持一个确定的 self edge；不支持混合/额外关系和未知 selector。

## 持久化、互斥和恢复

数据库升级为 v21，新增 `listing_corrections`、`listing_correction_attempts`；attempt 有每 correction 唯一约束。日志保存原身份、request/hash、revision/state、send intent、response/readback；终态发送历史不参与普通保留期清理。

`amazon_write_locks` 仍按原 seller/marketplace/SKU hash 全局互斥，新增 `owner_kind`/`owner_id`，旧锁回填 draft 所属。普通 PUT 与 correction PATCH、别名店铺/草稿共用该锁。普通 readback 不能释放 correction 锁；迟到普通 PUT 的 owner 不匹配时整段 draft/ledger 完成写入都跳过，仅追加其独立 exchange 证据。

状态：PREPARED → READY → SENDING → ACCEPTED → VERIFIED，以及 REJECTED/STALE/CANCELLED/UNKNOWN。一个案子最多一个正式 attempt；已拒绝后新案关联 previousId。服务重启把 SENDING 记 UNKNOWN，无自动发送。

备份校验包含新增表和 owner 列；恢复撤销未发送授权，保留当前所有已发送历史，包括已释锁的 VERIFIED/REJECTED。旧 READY 快照不能覆盖更新的发送日志，原 draft 不在快照仍保留必要 correction/attempt/锁证据；冲突保守锁定。修正状态写入带 revision CAS，避免跨服务实例的迟到失败覆盖已推进状态。

## 质量审查补修（原 cc8172b 后）

- 预览返回后再次核对当前配置、原提交、远端基线、PTD 与修正 revision；在途发生任何变化都不能进入 READY。预览响应本身仍保留。
- `package_contains_sku` 的每个出现元素须有可辨别的 SKU、目标站点及合法可选 quantity。`[null]`、`[{}]`、缺 selector 或错误容器都不能当作目标已消除：保留完整观测，明确“无法核实”，维持 ACCEPTED/UNKNOWN 及相应锁。合法空数组或字段缺失仍按原规则处理，UNKNOWN 不解锁。
- 恢复旧 ACCEPTED 快照时，只有当前已发送 VERIFIED/REJECTED 的可信日志、相同请求与完整身份、相同 correction owner，且当前确已无锁，才清除该旧快照锁。不同 owner、身份/请求冲突或缺少匹配旧案依据均保守 UNKNOWN，保留锁和发送 tombstone。
- 同类响应结构保护：畸形 issues 条目不能成为无 ERROR 的预览通过证明；正式成功 HTTP 携带无法判读的 issues 记 UNKNOWN，不重发。
- 上述缺陷均先用独立模拟回归复现失败；修正服务定向 36 项全部通过，`tsc --noEmit` 通过。未重复全量回归，未请求真实平台。
