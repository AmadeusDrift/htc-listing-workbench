# 自动任务未响应排查与调度修复

## 结论与边界

用户反馈进入设置和继续上架时出现 Electron 未响应。Windows 在 2026-10-11 16:46 记录 AppHangB1 / Application Hang；目前证据指向挂起，不是已确认的进程崩溃退出。

已复现一个能造成长时间未响应的根因：自动任务的 SKU 循环及后台回读循环使用连续的立即完成 Promise。它们的 `await` 只让出微任务，未给主进程窗口消息、IPC 和计时器提供执行机会。处理多个本地失败时，单项检查和失败分类各约数百毫秒，连续累积为数十秒。

这能解释继续任务时的未响应，也可能影响同时打开的设置页面；单独进入设置没有复现持续挂起，不能断言用户两次现象全部由同一原因造成。

## 复现方法与结果

- 使用最近安全快照的独立副本，包含 103 个任务项、94 份草稿；原始工作区和凭据未修改，未复制凭据。
- 启动前安装网络阻断，隐藏运行 Electron。隔离探针仅跳过因缺少凭据而失败的连接范围检查，继续过程中的外部请求一律阻断。因此这是批量本地失败路径的复现，不是正式上架验收。
- 原 2.0.0：首次测得主线程最大延迟约 34.7 秒；带 CPU 采样复测约 37.9 秒。93 次单项处理累计约 16.3 秒，99 次失败分类累计约 19.4 秒，各自单次最大约 301 / 255 毫秒，确认主要是连续累积阻塞。
- 修复后同一快照、同样断网条件及 CPU 采样：最大主线程延迟约 2.1 秒。整批处理仍约 47.8 秒；修复改善响应性，并不保证缩短整批工作时间。该次测量与全量测试并行运行，不作为精确吞吐量对比。
- 仍观察到候选商品扫描约 0.54 秒及草稿反复解析开销。它们是后续性能优化项，本次不混入无关改动，也不宣称完全消除卡顿。
- 探针和含真实数据的副本仅保留在被忽略的 `artifacts/`、`.test-data/`，不进入版本库。

## 修复

`src/main/automatic-listing/service.ts`：每个 SKU 之间通过 `node:timers/promises` 的 `setImmediate` 交还事件循环。恢复执行前重新检查运行状态；后台回读还检查任务 revision，避免暂停、取消或其他状态变化后继续使用过期状态。

新增两个回归测试，分别验证连续本地失败、后台回读期间的暂停必须在下一 SKU 前生效。原代码两个测试均以 `2 !== 1` 失败，修复后均通过。
