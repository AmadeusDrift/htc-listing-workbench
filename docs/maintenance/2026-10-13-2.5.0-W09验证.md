## 实施与数据所有权

- 采购行新增可选 `basis`：本地商品 revision、来源内容 SHA-256、配方 SHA-256、平台观察 SHA-256；新行冻结引用，旧行允许无此字段。保留既有 draftId、店铺/SKU、观察时间及完整配方。采购价格、数量修改不回写商品、销售配方、来源和提交。
- 人工保存仍执行 revision CAS；价格或采购单位发生变化，即使 IPC 传入 true，也撤销价格确认。保存后的再次确认读取新修订。旧行数量、价格及新版完整引用以 `audit_events.action=procurement.revised` 的 previous/current 保存，与批次更新同一 SQLite 事务。
- 采购展开增加 `originalPacks`，与实物件数、报价单位分别显示；现有采购 HTML/CSV 和界面共用的说明自动带出原包数、拆包/混装说明。实际采购数量和计划发货销售套数仍分别保留。
- 标签状态由 `item_labels` 拥有；采购 `get()` 投影当前标签状态，`setLabelStatus` 保留兼容通知签名但不再写第二套状态或增加采购修订。人工批次修订变化后，旧标签显示过期。
- 标签新增可选 `batchRevision`，新版本指纹绑定批次修订、数量、纸张/格式、店铺身份等。旧记录按原指纹可读，不修改旧文件；无修订绑定的旧请求次数、UNKNOWN/取消结果不会在升级时被清零或重放。
- 新增异步 `prepareVerifiedBatch` 作为生产 IPC 准备入口，READY 复用前重新核验完整 PDF 集合；原同步 `prepareBatch` 是保留给隔离测试的排队原语，生产调用已全部切到验证入口。损坏文件进入 FILE_INTEGRITY，人工重试以新 ID/新文件目录保存，对应 SKU 的旧 PDF 引用、错误和次数保留；重试两条记录变更在事务内完成。
- 商品数据页的采购入口携带店铺，行级入口携带店铺和 SKU；采购页仍使用服务返回的 eligible，不把 UI 的销售/库存数值推断为采购资格，并可取消 SKU 筛选。
- 人工货件逻辑已有实现：只接受人工保存号码；导入期间重新核对当前号；旧附件的 shipmentId 和文件不改；界面按当前号显示历史附件；LINKED_UNVERIFIED 不表示已发货或已入库。本包补验收，不重新实现。
- 无新增表，无 Schema 版本变更。没有修改 accepted-skus 的接受资格规则、定价规则或备份底层。

## A31 审查补修：UNKNOWN 不可由普通重试或修订重放

主进程审查复现首个版本的漏洞：新记录已有 batchRevision 时，采购价格/货件号修订导致标签指纹变化，prepare 新建 attempts=0 的版本；普通 retry 也能清除 REQUEST_UNKNOWN 后重新发送。上文“人工检查后重试”不适用于 REQUEST_UNKNOWN：它必须保留原请求并先核对，当前没有可证明原请求未发送的解除端口，因此普通重试保持阻断。

补修行为：

- sync/prepare 发现本批次本行任何未消解 REQUEST_UNKNOWN，返回原记录，保留 ID、请求 ID、次数和错误。采购价格、货件号、数量、授权轮换或格式改变均不能抹除该事实。
- retry 在修改任何记录前拒绝 UNKNOWN；明确安全失败仍沿用既有限次/人工重试规则。
- 实际调度与 beforeSend 的 matches 检查同一行历史 UNKNOWN，避免已排队新版本绕过保护。
- 在途旧版本被新修订替代后才返回 UNKNOWN，也把未知结果及真实请求 ID 写回原版本，并阻止新版本发送；不会丢弃晚到的未知结果。
- 增加负向合成回归：相同参数 prepare、改采购价、改货件号、普通 retry、每一步重启，均保留原身份且只有第一次请求。加密备份/恢复后 UNKNOWN 请求身份、次数和错误证据一致，恢复按既有规则置 paused=true。另测晚到 UNKNOWN 阻断已经排队的新版本。

备份新增断言首次失败仅因为恢复器按既有安全规则置 paused=true，已调整用例显式校验该行为，未改恢复器。最终补修验证：上述同一七组测试 **85/85 通过，0 失败/跳过**；`npm run typecheck` 与 `git diff --check` 通过。日志 `w09-unknown-tests.log` 为本地忽略产物。仅 fake transport 与合成临时数据库/PDF，无真实外部请求。自审检查了未知结果保存顺序、历史行阻断、重启/备份保留、明确失败的正常重试回归。在线和桌面实点未验范围不变。

## A31 二次审查补修：发送后进程崩溃

原构造器把 REQUESTING 和 DOWNLOADING 一并视为 INTERRUPTED，普通重试会再次 POST；且在途请求先变为 STALE 后，重启时无法从 status 发现仍在等待响应。

- ItemLabelRecord 新增可选布尔 `requestPending`，不影响指纹和 Schema 版本。进入 REQUESTING 时持久化 true；转为历史 STALE 时保留。兼容旧 REQUESTING 行转 STALE 时也补该标记。
- 明确收到响应后，一次写入 requestId、DOWNLOADING（若仍当前）和 requestPending=false；安全失败也清标记。未知结果直接持久化 UNKNOWN，避免先清在途再保存未知的崩溃窗口。
- 构造器把 REQUESTING 或任意历史 requestPending=true 记录转为 REQUEST_UNKNOWN，保留原 ID、请求 ID、attempts；当前行 FAILED、历史行仍 STALE，均暂停，普通重试阻断。
- DOWNLOADING 说明远端响应已知，恢复为 INTERRUPTED 并保留响应请求 ID；下方原成果下载恢复补充已限制人工重试只能使用原响应 URL 下载，不再重新 POST。
- 新测试直接写入 REQUESTING/attempts=1/requestId=first-request 模拟发送后未进入 catch 就崩溃，覆盖当前行及经修订变为 STALE 两种重启路径；均保留证据且零第二请求。另验证 DOWNLOADING 区分、运行时在途标记跨 STALE 保留以及明确失败重试回归。

## 原响应下载恢复（最终补修）

- 沿用已分离的 createMarketplaceItemLabels / downloadItemLabel 与 itemLabelDownloads 适配器；保存原标签响应后，后续恢复只调用下载，不会再次生成标签请求。
- 主进程专用 `amazon_settings` 前缀 `item_label_download_v1:<labelId>` 存储版本 1 的 labelId、fingerprint、原 requestId、receivedAt、受限 URL 和绝对 expiration；`storage/owners.ts` 登记为 labels 所有。合法响应身份与下载资料在同一事务写入；格式损坏的已知响应保留 responseReceived 标记，因缺少恢复资料而阻断。
- ItemLabelRecord 只增加 responseReceived/downloadAttempts 元数据，不含 URL。renderer、IPC、普通标签列表、日志和导出不返回下载能力；既有加密备份包含该 settings 记录。W10 已收到保护该前缀的通知。
- 恢复前重新验证记录身份、原 requestId、标签 fingerprint（已绑定数量/纸张/批次修订）、URL 来源和有效期；每份下载前再查期限。过期、缺失、错误绑定或旧 DOWNLOADING 无恢复描述时，明确阻断并保留原请求。不能借重试偷偷 POST。
- 损坏完整 PDF 的重试依然创建新文件版本并保留旧版，继承原 requestId/POST 次数与受限下载描述，仅重下原文件；下载次数单独记录，瞬时失败最多自动重试三轮，保留最初 POST 的 requestId，不将下载请求 ID 覆盖它。授权轮换后若恢复绑定不匹配也阻断，不转回 POST。下载失败不会累计成新的 POST。
- 合成回归覆盖直接持久化 DOWNLOADING 崩溃快照后重启、加密备份恢复后续下载、链接到期、错误 fingerprint、URL 不出现在标签列表，以及损坏文件新版本保持一次 POST。所有原 UNKNOWN/STALE/明确失败回归继续通过。

最终七组相关测试 **93/93 通过，0 失败/跳过**；`npm run typecheck` 与 `git diff --check` 通过。日志 `w09-recovery-tests.log`。无需新增表或 Schema 迁移。未触真实库/接口/任务，未合回集成；主进程仍需将 W10 的 REQUESTING 备份恢复规则与本包联合复验，在线、真实打印与 UI 实点未验证。

## 真实 Transport 接线复审（最终状态）

主进程复审指出此前 fake download 方法遗漏真实边界：AmazonTransport 的精确 URL 能力只在内存中，重启后即便 settings 有原 URL 也无法 GET；真实 GET 503 被转换为普通 UserFacingError，未进入服务的三轮下载退避。已用真实 Transport + fake fetch 先复现两项失败再修复。

- 新增仅主进程调用的 `AmazonService.restoreItemLabelDownloads(scope, documents)` → `AmazonTransport.restoreItemLabelDownloads(target, scope, documents)`。ItemLabelService 先校验本地恢复记录的原请求 ID/fingerprint/期限，再经实际服务与 Transport 校验店铺、卖家、站点、环境和授权代数，最后登记精确 URL 能力。
- Transport 能力 Map 从纯 expiration 改为带店铺身份与代数的记录。恢复仍经过 itemLabelDownloads HTTPS/官方来源/无嵌入凭据/有限期校验；每次 GET 前和异步 DNS 后重新核验能力与目标身份。清除指定店铺授权同时撤销该店铺内存下载能力。未删除白名单，也未给任意 S3/其他查询参数放行。
- GET 的 408/429/5xx 返回安全 AmazonTransportError（unknownWrite=false、无签名 URL、无响应正文），使真实 503 进入既有独立下载计数与退避；重定向、非公开 DNS、非 PDF 及过期能力仍拒绝。
- 服务级集成使用真正 AmazonTransport，只有最外层网络是 fake fetch：首次 POST 获得签名 URL，实际 GET 503 后持久化 DOWNLOADING；重新创建空能力 Map 的 Transport 并重启服务、加密备份恢复服务，都经恢复端口只 GET 原文件，POST 总数仍 1，原请求号和 POST attempts 不变。GET 保持 credentials=omit、redirect=manual，无 authorization/x-amz-access-token。
- 另一真实 Transport 集成验证 GET 503 第一轮进入 QUEUED 且 nextDueAt 在未来，到时共三轮、每轮最多两次下载（合计 6 GET），最后 FAILED/HTTP_503；只有 1 POST。额外负向验证错误店铺/代数、过期、非官方来源、其他精确 URL、私网 DNS 都在网络前阻断。
