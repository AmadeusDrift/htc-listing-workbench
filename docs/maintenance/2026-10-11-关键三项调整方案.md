# 关键三项调整方案

**目标：** 让可用的 AI 商品字段进入后续流程，让已收到的失败响应可以本地恢复，让旧任务实际采用已经确认的宽松策略。

**设计：** 在现有解析、调用日志、任务恢复入口修正三个根因，沿用当前流水线。商品字段按 Amazon 原规则处理；内部辅助说明不作为整份响应的拒绝条件。系统读取与 AI 观察合并，图片沿用对应 SKU 的来源关联。

**技术范围：** Electron / TypeScript / SQLite；用户已授权执行，三项按独立分支串行实施并通过回归。真实数据库未执行恢复、未启动业务任务；正式包交付见交付记录。

基线及范围见[问题总登记](2026-10-11-实跑问题总登记.md)。此次只处理 R01、R02、R03，以及它们直接需要的字段提示与恢复记录。

## 方案选择

| 选择 | 结果 | 建议 |
|---|---|---|
| 只补 transformation 的几个别名 | 能绕过首个报错，但下次新的说明句、引用异常仍可能整份失败；旧任务仍卡住 | 不作为完整方案 |
| 辅助信息兼容 + 字段局部处理 + 旧响应/任务恢复 | 复用现有产物，对应本批三个已证实根因，改动范围可控 | 采用 |
| 重写全部校验与任务调度 | 影响面大，混入尚未定位的问题，难以判断实际改善来源 | 本轮不做 |

## R01：AI 返回内容按字段处理

### 预期行为

例如 AI 返回 `transformation: "composed from source facts"`，商品颜色、材质等原生值仍进入正常处理。内部“怎么生成这个字段”的说明保留为备注，不再导致整份响应失败。

1. 提示词提供完整返回示例和建议的 transformation 值，减少歧义；接收端不依赖模型严格复述内部枚举。
2. 明确可识别的转换说明归一化；无法确定的说明保留原文并标记未分类，不统一假装为 compose/copy，不因此拒绝商品字段。涉及商品事实的判断使用实际字段值和来源，而不是靠这段备注决定通过。
3. `nativeValue` 为商品字段值，展示文本由它生成。展示投影不同、重复引用等可确定的格式问题由系统整理；不重写商品事实。相同字段重复且值相同可合并；值不同保留冲突信息，不取最后一条覆盖。
4. 来源引用先按原始请求上下文中的 evidence ID、SKU/事实 ID 明确关联。可唯一对应当前商品及其 SKU 的才转换；无法对应的记录在具体字段上，不模糊匹配其他 SKU。字段若已有当前 SKU 的直接来源依据，可按该依据评估；缺乏必要事实依据时仅该字段待补。
5. 候选逐字段解析和校验。某字段格式或引用有问题，其他字段仍保留；跨字段依赖只影响实际关联的字段。整份原文无法识别为有效结构时才记整份解析失败。
6. 必填字段确实缺失或不符合 Amazon 规则时指出字段、实际值、规则与原因；不适用的选填候选可省略，保留说明，不用选填错误堵住全商品。沿用完整 schema 及用户已确认的商品事实边界。

提示示例：“已保留其他可用字段；color 的来源引用无法对应当前规格，正在使用当前规格资料重新判断。”若没有足够资料则明确写“color 待补资料”，不写笼统的“AI 响应校验失败”。

### 改动入口和验证

## R02：收到响应与得到可用结果分开

### 预期行为

“AI 已经回答，但本地没解析出来”应显示可恢复的格式问题。点击继续任务时，先读取已保存响应，以新解析方式恢复，不再次支付同一份请求的费用。

| 已有证据 | 恢复动作 |
|---|---|
| 未发送请求 | 沿用正常执行入口 |
| 已收到完整响应，解析失败，原文仍在 | 本地重新解析并检查；可用字段继续，剩余问题具体列出 |
| 已知收到失败响应，但原文缺失或仍不可用 | 显示“已收到响应，无法本地恢复”及原因；按已有有界修复规则处理，不能变成自动无限重试 |
| 已发出但是否完成无法确认 | 保持待核对；核对服务结果/已有产物，不自动重发 |
| 已产出并采纳结果 | 复用已有结果，重启或重复点击不重复采纳 |

这是一套结果判定，不额外引入多层人工审批或一套复杂的新任务状态机。

1. `unknown()` 同时读取原调用完成状态与保存的响应，不再只用“没有成功 resultId”判断未知。只有完整响应/明确终态证据才能认定已收到；不能仅凭任何 FAILED 字样解除真正未知的请求。
2. 增加本地恢复记录，关联原 call ID、冻结上下文摘要、原文摘要、解析版本、恢复结果与字段原因。原调用失败和费用记录保留；不改成历史成功，不新增付费调用或费用记录。
3. 现有结果读取/采纳路径明确支持“本地恢复结果”。不能把恢复结果硬塞到只接受原调用 SUCCEEDED 的旧入口而继续报错。
4. 同一调用、原文和恢复版本只生成一份恢复结果；原文缺失时明确说明。恢复记录与候选引用一致落库；重启能从保存位置继续。
5. 恢复使用原冻结上下文理解旧响应；采纳前对照当前商品、SKU 和 Amazon 规则。资料已实际变化时，当前保留新鲜度阻断，不把旧响应直接写到另一商品；局部重判断与重采纳尚未实现，已登记 R21。本批 19 个上下文均未变化。
6. 暂停的任务不会因安装新包自行恢复。用户原有“继续任务”入口先本地恢复，再进入正常后续阶段；不要求清库、新建整批或多次手动解锁。

## R03：旧任务按新策略重新判断相应阶段

### 预期行为

旧任务点击继续，不能因为曾经保存过 DONE 或剩余错误清单，就永久复用旧审核结论。规则升级与真实商品变化应分开判断。

1. 审核缓存是否可用，同时看实际商品输入和审核策略版本；DONE 只表示过去执行结束，不表示旧结论永远有效。旧版本缺少策略信息时执行一次本地重新评估。
2. 只重算过期的 remaining 和相关字段判断。保持商品、已采纳的有效字段、已付费图片、提交记录及原始错误历史；不整批清空来源准备标记或重新出图。
3. 同一 SKU、同一来源图片内容，只是证据 ID、数据格式或策略版本变化：建立兼容关联并继续；图片是否可复用仍按实际商品与现行图片要求判断。
4. 规格、实际图片内容、店铺/站点等业务输入真的变化：明确指出变化项，重新处理依赖它的阶段。不能以“兼容旧版本”为由复用其他变体的图。
5. 同时覆盖旧 DONE 带 remaining、未完成图片规划、已完成图复核、继续任务和应用重启的入口；不能只修新建任务。
6. 原来“未被系统词表识别”“不属于指定依据类型”等内部限制，按已确认的宽松方案重新评估。存在确切冲突时定位对应属性；新策略仍无法解决的，显示当前原因而非继续显示过期缓存。

## 实施与交付次序

1. `fix/ai-field-response-compatibility`：R01，让已有响应可以被正确理解。
2. `fix/known-field-response-recovery`：R02，让这批已知失败响应真正进入本地恢复和采纳链路。
3. `fix/legacy-listing-policy-resume`：R03，让旧任务从正确位置采用新判断。

每个分支从最新集成结果串行推进，只包含本根因及必要测试、文档。按仓库约定本地提交并合并，未验证的项不写完成。不在这轮顺手改品牌、ROI、风险审核或全部调度架构。

已将三项合并后的程序用于隔离旧任务样本，记录“恢复了哪些、还卡在哪、是否产生新调用”。隔离验证和最终回归已通过，正式 2.0.0 已更新，保留 1.0.0 及可回退包；原工作区正常复开尚待确认，详见[交付记录](2026-10-11-三项修复交付记录.md)。

真实运行验收按代表商品走到字段采纳、图片处理、Amazon 提交/回读，分别记录阶段成果。平台仍拒绝的真实原因继续登记，不把“解析通过”“提交已发送”写成“上架成功”。已知的品牌、ROI、缺图等其他阻塞仍可能存在，因此这三项修复不承诺整批 103 个都成功。
