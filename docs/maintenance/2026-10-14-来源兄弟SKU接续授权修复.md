# 2026-10-14 来源兄弟 SKU 的手动接续授权修复

范围：只修正自动上架来源检查循环的任务上下文，不修改真实任务，不追加次数，不调用真实接口。

根因：生产环境总是注入 TaskBatchRuntime（即时模式也如此）。来源检查按同一商品的兄弟 SKU 连续执行，却沿用外层第一个 SKU 的 taskAiContext。第一个 SKU 被标为 FAILED 后，后续兄弟的 authorize() 仍检查第一个 SKU，导致有完整403回执并已显式继续的请求被错误阻断。原单独 AiService 测试没有覆盖这一生产组合。

修改：统一生成按当前 SKU 绑定的 taskAiContext；循环中每个兄弟独立携带 rowKey、lastContinuedAt、phase、waitingOperationId。授权仍检查选择范围、任务正在执行、内存授权、数据库当前 revision/status、当前行非终止状态；没有放宽403证据、原次数/预算和UNKNOWN保护。

验证：真实 AutomaticListingService + AiService + TaskBatchRuntime + 隔离 SQLite，所有 HTTP 为假服务。新增测试复现第一个兄弟失败、后两个403可重试的组合（修复前2次种子请求、后2个被错误阻断；修复后共4次假请求，首项保持失败、后两项完成）。另覆盖UNKNOWN不重发、暂停、取消、外部任务revision变化撤销授权。测试用假Amazon/图片/采购依赖，不证明线上模型成功。

截至此记录：专项5/5通过；typecheck通过；strict boundaries通过。来源服务+自动上架整文件初跑286项285通过，唯一失败是新增revision测试cleanup未同步隔离内存导致的检查点拒绝，测试已修正并5/5复测；生产行为并未为此放宽。最终整文件复测结果由主进程合并验收记录补充。

真实四个SKU的具体原始回执与任务快照尚未在本分支读取；这里证明并修复了可产生相同提示的生产调用链缺陷，不能把隔离成功宣称真实任务已经恢复。

最终整文件复测：automatic-listing + source-image-consistency-service 共287项，287通过、0失败、0跳过；日志 artifacts/auth-scope-tests-final.log。
