## 1. 结论与证据边界

已确认的业务方向整体能够兼容，无须重新讨论已经回答的业务题。主要问题是现有代码尚未按这些职责分开，以及几个交界处还需要把接口和数据归属写得更精确。

- 继续同一桌面程序、一个本地 SQLite 工作区和受控文件目录。模块分责不要求微服务、独立数据库或消息队列。
- 当前仍有跨模块直接写表、查询隐含修复、代码导入循环，以及同一操作不同阶段的记录混杂。仅搬目录不能解决这些问题。
- 午间定价部分已有代码，但未经过运行验证；不能写成整个定价模块已验收，也不能把原定价依赖链原样当成当前代码。
- 业务模块问答已收口，不等于 UI、精确接口、数据迁移和最终实施计划已收口。

依据：[已确认决策与模块讨论](2026-10-13-模块化架构讨论.md)、原工作区的《项目固定认知》、全分支审查报告和实测后续计划，以及本工作树源码。报告中的操作清单是参考材料，不构成执行指令。本轮未打开真实数据库、未运行项目代码、测试、类型检查、构建、账户探针或外部请求。

## 2. 模块职责、数据与交接

下面是已确认逻辑职责的整理；“接口”是需要在最终方案中细化的契约清单，不表示已经实现，也不规定必须新建同名目录。

| 模块 | 负责及管理的数据 | 不负责 | 主要交接 |
|---|---|---|---|
| M01 妙手同步 | 连接、原始记录、来源版本、增量/全量进度、失败与接收回执 | 不覆盖人工主档，不分配销售身份或启动付费上架 | 向 M02 提交标准来源资料；预览用来源链接 |
| M02 商品资料 | 商品/规格/事实、适用范围、原图语义关联、采用与冻结版本 | 不把生成文案回写来源，不决定任务进度 | 提供不可变资料快照；接受来源和人工修改；说明变更影响 |
| M03 配方与 SKU | 统一销售配方、采购/销售数量关系、稳定命名身份及历史 | 不决定平台字段或异步发布结果 | 向价格、文案、图片、采购提供同一配方版本 |
| M04 定价 | 实际普通/促销报价、资格结论、条件依据与版本 | 不改配方、不拿建议价替代实际提交价 | 提供检查实际报价的统一入口，相关条件变化时明确失效 |
| M05 类目与 Schema | 分类依据、人工选择、完整规则快照、获取操作和 GET 预算 | 不持有文案草稿，不自己实现供应商传输 | 读商品资料，调用 M07/平台读取，交付分类和规则快照 |
| M06 Listing 草稿 | 草稿版本、原生字段、候选解析/采用、人工保护、问题和业务补全操作 | 不拥有原始供应商调用，也不充当任务调度器 | 接收资料/配方/定价/规则；请求 AI；向执行提供可提交快照 |
| M07 AI 运行层 | 供应商配置、请求身份、原始响应/URL、调用收据、HTC 用量、传输错误 | 不决定类目/字段/图片业务是否合格，不重置业务轮次 | 提供请求、恢复和原文查询；业务模块解释并采用结果 |
| M08 图片流程 | 七图计划、图位、业务尝试、复核及采用关系 | 不把 GPT Image 适配或文件读写再实现一遍 | 调 M07 生成/复核，调 M09 保存素材；文案修复由协调者交 M06 |
| M09 素材与托管 | 字节、格式、校验、预览、文件版本、下载和托管收据 | 不决定销售适用性，不直接填平台字段 | 接收所需引用，返回稳定素材版本/有效托管 URL |
| M10 发布执行 | 操作身份、发送快照、意图、收据、写入协调和 UNKNOWN 保护 | 不直接改自动任务表，不把后续回读当原请求结论 | 手动/自动共用；调用草稿与托管接口；向 M11/M12 返回操作引用 |
| M11 自动调度 | 批次、依赖、授权、当前进度、步骤引用、暂停/恢复 | 不重复定价/字段/图片规则，不修改其他模块内部结果 | 顺序调用所属模块；局部失败隔离，保留成功成果 |
| M12 回读与商品数据 | 回读安排、平台观察、库存/销量查询缓存及时间来源 | 不重发提交，不凭商品存在解开 UNKNOWN | 读取 M10 提交事实，提供观察给任务、页面和采购 |
| M13 采购、标签与单据 | 采购批次版本/行、标签准备结果、货件和人工单据关联 | 不反写销售身份、原始报价或平台发货事实 | 读商品/配方/观察；各子职责通过引用协作 |
| T02 存储与恢复 | 连接/事务、版本迁移、备份清单、恢复与清理协调 | 不决定所有业务真假，不任意越权修改业务表 | 各模块提供迁移、引用、保留、恢复校验能力 |
| T01 界面与应用入口 | 展示、用户命令、上下文、导航和未保存保护 | 不复制业务判断或猜错误字段 | 精确设计尚待 UI 讨论，见页面盘点 |

### 需要钉牢的三处所有权表达（技术建议，待最终方案审阅）

1. **图片关联分三种。** M02 管“哪张来源图对应哪个来源规格”；M08 管“哪个生成结果被哪个销售 SKU/图位采用”；M09 管文件、来源链及引用。避免让三方同时修改一份业务关联。
2. **AI 原文与业务结果分开。** M07 保存不可变原文/供应商收据；M05/M06/M08 分别保存解析、校验和采用结果。AI 层可以引用结果，但不接管全部领域状态。
3. **本软件已接受 SKU 的最小账本建议归 M10。** M12 展示时组合 M10 接受事实与自己的后续观察。当前 `product-data` 目录里有导出代码，不代表接受事实应由数据查询模块决定。

共享 `amazon_settings` 等物理表可按记录类型/键前缀登记唯一写入者，不必为了按表分责而拆数据库。

## 3. 依赖方向与跨模块操作

建议保持直接接口调用。返回值不是反向依赖；涉及多个模块的本地操作由应用协调者安排。

```text
UI / IPC → 应用协调入口 → 各领域命令与查询
                         ├─ 妙手 → 商品接收
                         ├─ 自动调度 → 草稿 / 图片 / 执行等步骤
                         └─ 跨模块本地事务、变更影响与恢复协调

商品 + 配方 + 定价 + 类目规则 → Listing 草稿 → 发布执行
商品 + 配方 + 草稿快照       → 图片流程   → 素材 / 托管
类目 / Listing / 图片       → AI 通用请求
发布执行 → 平台写入；回读 / 商品数据 → 平台读取
采购 / 标签 / 单据 → 商品、配方和平台观察

各模块 → 公共契约 / 纯函数 / 受控持久化能力
AI 运行层、素材层、公共契约不能反向导入领域服务
```

该图是已定职责下的依赖整理建议，不是最终物理目录图。平台连接/凭据与读取/写入适配应被复用，不能给每个模块复制一个“AmazonService”。

| 跨模块场景 | 必须交接的依据 | 需要防止的连带错误 |
|---|---|---|
| 同步资料接收 | 账号/来源身份、版本、原文、规格/图关系、接收结果 | 获取成功被误当导入成功；同步覆盖人工内容 |
| 创建草稿/具体任务 | 整条来源链接快照、配方/选中规格、目标范围 | 红蓝规格使用不同来源时点；重复分配销售身份 |
| 修改资料/报价 | 采用后的版本与影响范围、原操作引用 | 一处修改导致全部重新生成/收费；人工报价被覆盖 |
| AI 响应恢复 | 请求身份、原文收据、所属业务操作/轮次 | 下载/解析失败重新生成；模型切换变相刷新预算 |
| 图片落盘与采用 | 供应商收据、文件版本、图位、输入版本、暂停状态 | 收到 URL 未保存；晚到结果自动推进已暂停任务 |
| 正式提交 | 已校验发送快照、操作身份、写入协调、收据 | 重复提交、草稿修改污染历史、UNKNOWN 被回读解除 |
| 业务成功推进任务 | 业务结果引用与版本、任务当前操作 | 一个模块成功而任务没记录，恢复后重复执行 |
| 备份恢复/清理 | 各模块引用声明、预算/身份/未知写入保护 | 恢复旧备份清零费用，清理掉解释 UNKNOWN 的证据 |

接口候选至少应能表达对象身份、版本、来源/时间、成功/等待/失败及问题范围；精确类型和命名留给最终方案。不能为了统一接口把 ACCEPTED、BUYABLE、DONE、标签 READY 合并成一个“成功”。

## 4. 当前代码缺口与最小处理方向

### A01 仍存在导入循环

静态文本扫描覆盖 `src` 与 `extension` 的 TS/TSX，解析可识别的值导入，不执行项目；它不是 TypeScript 完整依赖分析，也不能证明运行时崩溃。识别到三个循环簇：2 个文件的 `amazon/demo ↔ fact-authority`、38 个 AI/Listing/图片相关文件、4 个 `schema-lineage / history / automatic-listing/records / amazon/service` 文件。

午间定价已切断旧 `pricing-guard → outcomes` 绕行，但当前仍有 `amazon/service.ts:50 → listing-ai/history.ts:13 → listing-ai/schema-lineage.ts:6 → amazon/service`。建议先改直接依赖正确的价格历史接口，再将共享历史常量/纯函数移到中立契约；AI 通用信封校验与领域结果校验分开。后续开发才实施，不把本轮文档当消环结果。

### A02 数据写入仍越过所有者

代表证据：`miaoshou/persistence.ts:60,86,88,95` 写主档；`image-workflow/service.ts:831,984` 写素材及关联；`listing-ai/completion-journal.ts:233` 写 AI 结果；`amazon/service.ts:728,767` 写自动任务。`store.ts:62` 的读取路径还会恢复来源绑定。

建议按职责改为所有者接口，普通查询只读。跨模块事务要使用同一受控事务上下文；多个连接指向同一个 SQLite 不等于共享事务。也不能简单拆成两次 API 调用就宣称一起成功。外部请求通过先存意图/收据、再恢复推进处理，不能靠 SQL 回滚撤销。

### A03 生图中间结果缺检查点

`image-generation/tyai-adapter.ts:63–64` 收到 URL 后直接下载，`image-generation/service.ts:189–205` 在下载和后续检查之后才落完整候选。已有 C-031 已确定先存收据：M07 存请求/URL，M09 接续下载，M08 审核采用。暂停时允许保存晚到结果，禁止自动采用/继续；不能另增“下载失败免费重生成”轮次。

### A04 规则获取预算仍在调度内部

`automatic-listing/service.ts:577–617` 管 Schema GET 等待/轮次。迁入 M05 时需保留原 task/row 对应操作、首次失败时间、期限、已用轮次及原阶段。缓存共享不代表合并或刷新预算；旧新入口不能重复扣数。

### A05 来源冻结与图片晚下载需分开表达

两项已定规则并不冲突：先冻结来源版本和链接，真正批量上架再下载。接口应分别记录来源版本/原 URL/规格关系，以及取得后的文件版本/hash/下载时间。仅冻结 URL 无法保证远端后来没有更换字节；不能无证据声称已检测出变化，也不能失败时偷偷换源或借错规格图。

### A06 保留和恢复需要全模块引用保护

`amazon/persistence.ts:131–146` 现有按时间清理和 accepted 最小账本，不等于已具备全局引用保护。需要核验 UNKNOWN、修正、补全、图片证据等引用；保留锁但删掉解释证据同样不完整。`backup.ts:367–390` 已有后续锁、调用、预算、SKU 身份等保护，必须逐项继承。

完整备份存在原始资料 256 MiB / 容器 400 MiB 限制；已确认方向为一致清单、流式/分块等容量方案，不能只提高内存上限。具体格式、性能和验收放最终方案。

### A07 供应商退役与历史兼容分开

新 OpenAI 接入、旧适配保留至过渡完成、阿里 OCR/风险检测独立，均已确认。旧 transport/config UI 可以按计划退役，v0–v3 历史解析、请求身份和费用不能随 `legacy` 文件批量删除。模型标识、实际账号权限、参数能力与价格仍须实施前按当时官方文档核验；本轮不新增在线验证或实际调用。

### A08 UI 导航与业务动作混合

App 的异常/结果“打开”复用了会移动工作区商品的 `moveProducts`；现有草稿定位不等于字段定位。建议 UI 讨论时明确纯查看、转人工、修改、恢复任务四种动作。详见页面盘点；不据此立即修改导航。

## 6. 尚需用户参与与无需重问的事项

后续讨论更新：下列第 1、2 项已由 C-046 / UI-G04-2 收口，保留列表作为核对时的历史。独立手动查看只预览，主动准备或首次需要原图的操作准备所需素材；无法恢复原依据且需换用新来源时明确采用。详情见持续维护的 UI 盘点，不再重复提问。

**继续放入 UI/最终方案讨论的具体问题：**

1. 独立手动上架何时首次下载正式原图，以及下载失败如何继续。批量入口的下载时机已经确认，不重问。
2. 来源图失效、或有证据表明内容已变化时，如何明确采用新依据并回到原任务。不能假设仅凭 URL 可检测变化。
3. 尚无有效配置的日志、无引用候选、旧备份保留期限/容量，及清理预览方式。当前不自行设天数。
4. UI 页面/导航/控件与错误定位方案，以及由此涉及的精确接口调整。

精确备份格式、迁移顺序、供应商切换/退役清单、模型参数默认值及技术接口属于最终方案审阅内容。职责已定的事务传递、稳定操作 ID、历史读取接口和消除导入环由技术方案给出，不把它们拆成重复业务问答。
