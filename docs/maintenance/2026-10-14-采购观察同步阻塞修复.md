# 采购观察同步阻塞修复（2026-10-14）

## 已确认根因

2.5.0 主进程的实际 12.17 秒 CPU 采样中，`refreshWaiting` 占 7.265 秒，`procurement.candidates` 占 6.980 秒，`getProduct` 占 6.427 秒，`restoreWorkflowSourceBindings` 占 6.390 秒。每五秒的后台采购观察对全部候选草稿调用带历史修复的商品读取，同商品多 SKU 重复深校验图片流程。

此结论来自主调查任务采样，未从“输入 API Key”表象推断解密故障。实际隔离副本有 14 商品、101 草稿、111 图片流程、1749 AI 调用，Batch 项与收据均为零；本次不修推测的 Batch 热点。

## 第一阶段

采购投影显式依赖 `getProductSnapshot`，不调用修复关联的 `getProduct`。一次同步候选扫描按商品复用来源快照与回执，扫描结束即丢弃缓存。最新同 SKU 去重、UNKNOWN、父子体、备货资格、原始采购价和销售组合判断保持原逻辑。

- 两项新增测试先红后绿：只读候选禁止历史修复；同商品跨 SKU 每轮只读一次且下轮立即看见修订和价格变化。
- TypeScript 与 diff 检查通过。
- 采购、标签、暂停回读边界、自动文档备份四套测试共 105 项通过。首次普通 Windows 沙盒因 `realpath EPERM` 导致文件相关测试失败，非沙盒同命令全部通过；没有更改生产逻辑绕过错误。
- 主调查任务使用隔离副本验证：101 候选、5 合格；三轮 631/610/580 毫秒，`getProduct` 调用零，`getProductSnapshot` 共 39 次（每轮 13 商品）；保护表不变，外部请求零。

第一阶段仍有约 0.6 秒同步扫描，后续增加后台观察的协作式分段。此记录不代表正式安装包已替换或真实上架已验收。
