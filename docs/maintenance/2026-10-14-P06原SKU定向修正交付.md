# P06 原 SKU 定向修正交付（2026-10-14）

范围：UI-OPT-010 / D08 / D09。独立分支 `feat/htc-250-sku-corrections`，仅修改本工作树。未触真实库、正式 EXE、Amazon/FTP/付费 AI，未 push。

## 实现

- 复用可信 ACCEPTED 原提交身份、原 SKU、冻结 PATCH、UNKNOWN 写锁及 correction/attempt 表；无 SQLite 迁移，不占 Schema31/32。
- 保留核实的独立 SKU 包装自引用删除；合法非自引用包装字段不会抢走普通字段修正。复杂父子关系仍具体转人工。
- 新增两种确定性规则：已有可信提交事实在当前 Schema 中唯一匹配的大小写/首尾空白枚举规范化；用户已确认的 `dangerous-goods-fixed/v1` 固定 `not_applicable`。只对当前回读中有 code/message/ERROR/attributeNames 的问题处理，不猜缺失事实。品牌、制造商、类别、GTIN/标识、父子/包装复杂关系、缺少确定规则或原值冲突转人工，并附平台错误。
- `AmazonService.continueCorrection(input:unknown, confirmed:boolean)` 编排：PREPARED/READY → 验证 → 冻结发送 → 回读。现有 `sendAmazonCorrection({id,revision,patchHash})` IPC 在主进程原生窗口展示范围、前后差异、依据和轮次后调用；同一次确认最多自动两轮。第二轮只能在首轮批准范围内，载荷必须不同，规则仍确定、身份及事实链仍匹配。UNKNOWN 只核对；回读匹配也不能解除 UNKNOWN。
- 自动第二轮可以复用已知 ACCEPTED 修正的精确匹配回读事实，但不能把观察到商品存在当作未知发送成功。
- 同问题上限采用保守字段交集：历史发送的字段与本次任一字段重叠即计入相关轮次。上限和无变化检查从不可重放发送账本计算，发送事务内再次检查；取消、单纯预览不消费轮次。未知/失败/已完成历史和两轮 request/response/readback 均保留。
- 新记录 `correctionVersion:2` 及 scope/evidence/problemKey/round 有严格验证，范围须与冻结 PATCH 路径完全一致。旧记录仅兼容原来的单一自引用删除；删掉版本元数据不能把普通字段 PATCH 降级成旧合同。get/list、backup 的 assertCorrectionHistory 使用该验证；已有备份恢复撤销发送授权逻辑保留。
- 生产 ListingCorrectionPanel 显示前后差异、依据、轮次、保留平台问题和各历史请求/响应/回读；PREPARED 可以直接“继续并确认修正范围”，无需逐字段/逐轮确认。原有手动预览仍可用。

## P05 接入合同

P05 的 READBACK 仅导航原草稿的修正面板/准备入口，不能将 ACCEPTED SKU 交普通重跑上传，也不能绕过原生确认调用底层 send。准备调用现有 `prepareAmazonCorrection({id:draft.id,revision:draft.revision})`，只做核对/规划；真正继续调用上述既有 sendAmazonCorrection 路由。返回最后一轮 ListingCorrection；可为 VERIFIED、ACCEPTED 等待回读、UNKNOWN 锁定、REJECTED 停止或 CANCELLED（下一轮超出范围）。平台字段修正核实不等于可售。
