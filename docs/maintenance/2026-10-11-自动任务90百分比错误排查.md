## 集中失败根因及离线复现

通过运行中的正式程序读取对应工作区数据库与已有 ai-diagnostics，未调用外部服务。61 次失败中只剩最近 50 份原始响应证据：当前诊断保存上限为 50，前 11 份因轮转不可逐条验证。

将这 50 份响应传入现有 validateConsistencyOutput / assertConsistencyOutput，50 份全部复现拒绝。响应存在：

- 44 份额外携带顶层 `type: json_object`；严格 keys 校验仅允许 kind、assets，因此拒绝。
- 29 份缺少 `kind: source-image-consistency`。与上一条存在重叠，不能相加为不同 SKU 数。
- 32 份把原始 fields 的 ID 当作 claims 的 ID。典型请求 claims 为空，但模型按 4 个原始字段生成 4 个核验项；部分值还把多个颜色拼成一个字符串，或者直接复制型号。

仅在离线副本中去掉上述 type 并补齐固定 kind 后，继续执行原有严格校验：18 份可通过协议校验；27 份仍因 claims 数量不符被拒绝；5 份仍违反枚举值约束。此操作用于定位，不曾将副本写成有效结果或商品资料；协议可通过也不意味着图片与规格匹配。

对应代码：

- `src/main/source-image-consistency/adapter.ts`：提示同时发送 fields 与 claims，采用概略对象模板，缺少空 claims 示例以及明确禁止使用 fields ID 的说明；与实际服务响应协议不一致。
- `src/main/source-image-consistency/comparison.ts`：严格验证顶层字段、有限值及精确 claims/图片关联。该保护不能通过随意删除核验项、重写 ID 或直接给 MATCH 来绕过。
- `src/main/ai/service.ts` 的 observeSourceConsistency：已存在 attempt 却没有有效 result 时，直接重现保存的 OUTPUT_INVALID。这解释了再次点击继续为什么会很快停下：当前代码不会自动重新付费请求，也没有完整的失败响应恢复流程。
- `src/main/ai/output-diagnostics.ts`：最多保存 50 份拒绝证据；本轮 61 次失败超过上限。该证据容量不足已成为后续无重复付费恢复的限制。

因此主要根因是来源观察请求/响应协议及失败恢复衔接问题，不能把 61 个系统校验失败当作 61 个商品不合格。模型错误生成字段 ID 是真实观测；“提示边界不足导致混淆”是代码与响应对照得出的解释，仍需用改进模板的测试验证，不能保证改提示后所有实际响应都正确。

## 建议修复顺序与范围

1. 优先修复来源观察协议：明示固定 kind、空 claims、逐项 ID 和单一有限值；在有明确边界且保留原始证据的前提下处理已知格式外壳，不能放宽图片/规格一致性。
2. 设计已有 OUTPUT_INVALID 的本地再解析与安全恢复：可合法解析的证据重新评估；仍含实质错误或已轮转丢失的证据明确列出，不自动重新付费。不得把 18 份协议可解析写成 18 份可上架。
3. 再处理 13 项缺少关联、6 项不确定、19 项历史未知，以及 3 项平台限制；分根因推进，不用单次“继续”重跑全部。
