## 3. 现有系统的运行形态

这是一个本地 Windows 桌面工作台，现有技术栈是 Electron、React、TypeScript、Vite 和 Node SQLite，另有浏览器采集扩展及 C# 原生通信宿主。它已有业务目录和服务类，尚不能据目录名称认定职责、接口和表的所有权已经隔离。

```text
React 页面 / 本地编辑状态
    ↓ window.red（共享类型 + preload 中显式方法）
Electron IPC（调用者检查、参数数量检查、恢复期间限制、错误转译）
    ↓
主进程应用装配、业务服务、后台任务与外部请求
    ├─ red.sqlite：同一工作区数据库，多服务各自持有连接
    ├─ 文件：原图/预览、生成候选、标签/单据、缓存、凭据、备份
    └─ 外部：妙手、Amazon、模型/OCR/图片风险服务、生图服务、FTP/公网图片

1688 页面 → 浏览器扩展 → Native Messaging → C# 宿主
    → Windows 命名管道 → CollectionBridge → 来源回执与商品资料
```

关键依据：`src/main/index.ts`、`ipc.ts`、`preload.ts`、`database.ts`、`src/shared/contracts.ts`、`extension/worker.ts`、`native-host/Program.cs`。

运行特点：

- 主进程入口集中创建服务、注入回调、启动后台观察并安排退出/恢复顺序。分类、父体准备、字段修复等业务协作也有一部分写在入口回调中。
- UI 使用受控 IPC；生产页面禁直接网络连接，关闭 Node integration，启用 sandbox 和 contextIsolation。此处描述现状，不等于全安全审计。
- 业务数据库为 `red.sqlite`，源码 Schema 版本为 21。既有规范化表，也有承载版本化业务记录的 `record_json` 表。
- 数据不全在 SQLite：商品数据使用 `product-data-cache` 文件缓存；生图候选包含图片、预览和 `candidate.json`；凭据由各自 vault 结合安全存储处理。
- `App.tsx` 的导航包括采集箱、手动上架、自动上架、上架进度、商品数据、采购备货、发货与标签、类目库、操作记录及设置。页面分区与业务模块边界不是同一回事。

## 5. 核心数据流与身份链

### 5.1 来源进入工作区

1. 浏览器采集经 CollectionBridge，或妙手通过请求/同步获取来源快照。
2. 保存来源回执、来源规格到本地 variant 的映射，同时创建/复用本地商品。
3. 原始采购标识、来源规格/价格与本地编辑值有所区分；原图关联还涉及来源证明和人工决定。
4. 商品被分配到采集箱、手动或自动工作区。这只是工作位置，不能当作 Amazon 上架状态。

### 5.2 自动上架主链

```text
商品 + 来源回执 + 当前业务规则
  → 销售配方/代表规格选择 + SKU 命名身份
  → 来源图片准备/一致性检查
  → 分类 + Amazon Schema + 父子关系解析
  → 草稿 + 固定规则/定价
  → 图文准备（字段补全/复核 ↔ 图片规划/七槽生成与审核）
  → 必要时准备父体
  → 执行任务：上传 → 图片属性 → 本地校验 → 平台预览 → 正式提交
  → 回读建档/关系结果 → 备货资格 → 建立备货批次 → 自动行完成
                                                   ↓
                                             按需准备商品标签
```

这是主干，不是所有分支的精确时序。旧结果复用、Schema 延迟续试、字段补修、父体等待、规则淘汰和暂停等会改变路径。`image-workflow` 内部创建/调用 ListingAiService，因此图文阶段目前并非严格单向。

自动处理成功的行当前完结条件包含跟进 READY、备货候选 eligible 和批次建立；标签不再是完成条件。整批任务在各行均为 DONE 或 SCREENED 时也会标为 COMPLETED，因此批次完成不表示每个 SKU 都上架成功。**自动行 COMPLETE、批次 COMPLETED、平台 ACCEPTED、BUYABLE、标签 READY 必须分别解释。** 依据：`automatic-listing/service.ts` 的 `refreshWaiting()` / `summarize()`，以及 `procurement/service.ts` 的 `candidate()`。

### 5.3 手动入口、修正与查询

- 手动页面经 IPC 使用相同底层草稿/字段/图片/发布服务，但部分编排与校验入口不同；不能只保证自动链路正确。
- 已提交 SKU 的修正使用单独的 correction 记录、预览、确认和一次写入尝试，保留原身份及提交历史。
- 商品数据查询依赖最小已接受 SKU 账本，保存带范围的派生缓存；不等同于更改上架草稿或重试提交。
- 备份恢复涉及整体工作区以及后续产生的安全历史，不能按“复制回旧数据库”理解。

### 5.4 已存在、后续必须逐项厘清的身份

`来源商品/来源 SKU → 本地 Product/Variant → SalesRecipe → SKU 命名分配 → AmazonDraft（店铺/站点/销售 SKU）→ 请求/业务操作 → 平台观察/备货行`。

它们不是同一个 ID；名称、展示规格、采购数量、销售数量、variation 父子关系及商品包装关系也不能直接互换。哪些对象共享、哪些按店铺或站点分开，属于后续架构讨论，不在本轮重新定义。

## 6. 主要依赖问题和写入现状

### 6.1 初始基线依赖回路与午间代码后的变化

下图记录初始基线，不能原样当作午间定价改动后的现状：

```text
amazon/service
  → amazon/pricing-guard
  → automatic-listing/outcomes
  → listing-ai/history
  → listing-ai/schema-lineage
  → amazon/service（导入 FAMILY_REBIND_EVENT_SUMMARY）

amazon/demo ↔ amazon/fact-authority
```

在午间工作后的 `07492e8` 基线上，定价 guard/outcomes 已改依赖 pricing 模块，原长链被切断。但仍有 `amazon/service → listing-ai/history → listing-ai/schema-lineage → amazon/service` 短环，demo/fact-authority 互依也仍在。当前静态扫描识别到 2、38、4 个文件的三个循环簇；扫描只解析可识别的值导入，不是完整编译依赖证明。见[整体架构核对稿](2026-10-13-2.5.0整体架构核对稿.md) A01，不能宣称已整体消环。

此外，`ai/validation`、`listing-ai` 的证据/兼容校验与 `image-workflow` 的历史/上下文校验存在更大的互相依赖簇。不能将“多个服务使用类型接口”误认为实现层已经没有环。

这些是维护边界问题的证据，**没有据此声称发生了运行时循环加载崩溃**。同样，共用 SQLite 并非缺陷；要讨论的是写入权限、事务协调与状态责任。

### T02 存储、备份与恢复（整组已确认）

5. **T02-5 恢复旧备份的协调。** 建议恢复前保存当前可恢复状态并处理在途操作，整体工作区通过单一协调入口恢复，不能各模块分别替换一半数据。沿用保留备份之后已发生的费用/尝试、SKU 分配和未知提交保护；不能因为恢复了旧业务画面就再次发出相同写入。恢复后不自动启动原任务、付费调用或发布，先核对身份和状态，再由用户继续。恢复中断要能明确完成或回退本地阶段，不能清空审计伪造成功。
